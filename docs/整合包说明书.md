# QDIP 整合包说明书

本文件面向要维护或接手本构建仓库的人（包括未来的 AI agent）。它讲的是「当前实现是什么、为什么这样、怎么改」，不是规格、不是计划。

术语以 `CONTEXT.md` 为准：便携环境、哨兵、首次运行门控、包布局、输入校验、产物校验、技能库、组件清单、分发模板。

本文件是维护者文档，留在仓库里，不随整合包分发。玩家上手教程见 `templates/玩家使用指南.md`，本文件不重复。

## 1. 这个仓库是什么

本仓库是**构建仓库**，不是整合包本身。它把外部组件（opencode CLI、便携 Node、插件、技能）与分发模板组装成一份可解压即用的 **QDIP 整合包**。

| | 构建仓库 | QDIP 整合包 |
|---|---|---|
| 位置 | 仓库根 | `build/qdip-generic-<version>/`（目录）与 `build/qdip-generic-<version>.zip` |
| 消费者 | 维护者 / 接手者 | 终端玩家 |
| 进 git | 是 | 否（`build/` 在 `.gitignore` 内） |
| 内容 | 构建脚本（`tools/`）、分发模板（`templates/`）、文档 | 运行时、配置、插件、启动器、玩家文档 |

三个角色：

- `tools/` 是构建器。`tools/build.ps1` 是主入口，`tools/components.json` 声明外部组件来源，`tools/layout.json` 声明包布局。
- `templates/` 是分发模板源。启动器、引导服务源码、配置模板、玩家文档的源头；它们本身不参与运行时执行，只是被复制进产物的原件。
- `build/` 是产物，不是仓库的一部分。`tools/cache/` 是离线制品缓存（便携 Node、opencode 离线包），同样不进 git。

版本号只有一个来源：`tools/components.json` 的 `version` 字段（当前 `0.5.0`）。它同时决定产物目录名 `build/qdip-generic-0.5.0/` 与 zip 名。

下表以一次成功构建（`build/qdip-generic-0.5.0/`）为准。「谁写」指谁把它放进产物，「谁读」指运行时谁消费它。产物内路径均相对包根。

| `启动.bat` | 构建（`launcher`，源 `templates/启动.bat`） | 玩家双击；内部调 `env.bat`、`opencode`、`setup/guide-server.js` | 否。主入口 |
| `进入环境.bat` | 构建（`env-shell`） | 玩家双击（通常经 Windows Terminal 的 `cmd /k`） | 否。启动器经 Windows Terminal 以 `cmd /k` 调用它进入环境 |

两个容易踩的点：

- `setup/` 是 `dir` 内容合并，源是 `templates/setup/*`，但该条目带 `exclude: ["*.test.js", "codemap.md"]`：`build.ps1` 在复制后用 `Get-ChildItem -Recurse -Filter` 按 basename（大小写不敏感，命中任意深度）删除这些项。因此 `templates/setup/config-writer.test.js`、`templates/setup/guide-server.test.js`、`templates/setup/codemap.md` 只留在仓库，不进产物；产物侧由 `layout/excluded-present` 规则守住。
- `opencode/config/opencode/` 是 opencode 在 `XDG_CONFIG_HOME` 下自动追加 `opencode` 段后的实际读取目录。产物里只有四份配置与 `local/`、`skills/`；`instructions/` 由运行时创建（见上表）。

许可一栏与 `README.md` 的「组件来源清单」一致：全部 MIT。

**为什么只有 2 个受版本闸门保护。** 闸门（`tools/check-sources.ps1`）的机制是：在组件的 `source` 目录里找到 `verifyVersion` 声明的 `exe`，用 `args` 运行它，把 stdout 与 `version` 比对（可选 `strip` 前缀）。这要求「有一个稳定可执行的探针，且版本串就是它的输出」。目前只有 `node.exe` 与 `opencode.exe` 满足。

其余 9 个没有声明 `verifyVersion`，原因分两类：

- 版本串是人工标签，没有对应的可执行探针：`latest`（omoslim-append）、`2.2.18+patch-kit`（omoslim）、`2.2.18-deps+tui`（omoslim-runtime）、`3.8.3-deps`（quota-runtime）、`2026-09-11`（matt-skills，日期）。
- 组件是目录而非单一可执行制品，或虽有纯数字版本但未接线探针：`omo-skills`、`opencode-quota`、`chrome-devtools-mcp`、`windows-terminal`。

也就是说，闸门只覆盖「可机器读取」的组件；其余组件的版本正确性靠维护者更新 `components.json` 时的纪律，以及构建时的产物校验（见第 5 节）。给一个组件加探针的做法见第 7 节。

## 4. 构建流水线

入口（从仓库根运行）：

```
powershell -ExecutionPolicy Bypass -File tools\build.ps1
```

`-SkipZip` 只产出目录、不压缩，用于开发迭代。

脚本开头做两件事，都是为了让相对路径可解析：`Set-Location $root` 把 CWD 锚定到仓库根；读 `components.json` 得到 `version` 并算出 `$outDir = build\qdip-generic-<version>`。**CWD 必须是仓库根**——`check-sources.ps1` 与 `verify-package.js` 都按 CWD 解析 `components.json` 里的相对 `source`。

`$ErrorActionPreference = 'Stop'`，任一阶段失败即 `throw`，Fail-Fast。

### [1/5] 清理
删除已存在的 `$outDir` 并重建。产物是「全量重建」，没有增量。

### [2/5] 复制组件
遍历 `components.json` 的 `components[]`，逐条 `source -> target`。语义是**目录内容合并**：先建 target 目录，再 `Copy-Item "$src\*" -Destination $dst -Recurse -Force`。不能直接复制目录到已存在的 target——那会嵌套成子目录（历史事故：`quota-runtime` 落成 `node_modules\node_modules`）。`omo-skills` 与 `matt-skills` 因此能合并到同一个 `skills/` 目录。

复制后有一段 Windows Terminal 专用处理：在 `runtime\terminal\terminal-*` 目录里写 `.portable` 标记文件，激活 WT 便携模式（设置与状态存包内 `settings\`，不污染玩家系统）。

### [3/5] 部署模板
读 `tools/layout.json`，遍历 `deploy[]`：

- 非 `optional` 条目源缺失：在复制前抛出 `部署条目 <name> 的源缺失：<src>（layout.json 未标 optional）`，不落到 `Copy-Item` 的原始报错。
- `optional: true` 且源缺失：打印 `(skip) <name> 源缺失，跳过` 并跳过（当前 `deploy` 15 条均非 optional，该分支暂无条目命中）。
- 否则按 `kind` 分派：
  - `file`：先建 target 的父目录（`Copy-Item` 不会自动建），再 `Copy-Item -LiteralPath`。
  - `dir`：建 target 后按内容合并语义复制 `"$src\*"`；若条目带 `exclude`，复制后用 `Get-ChildItem -Recurse -Filter` 删除 basename 命中的项，并逐条打印 `  - <name>: 排除 <相对路径>`。
  - `emptydir`：只建 target 目录。
  - 未知 `kind`：抛错。

`source` 相对仓库根，`target` 相对产物根。**增删部署条目只改 `layout.json`，不改 `build.ps1`。**

### [4/5] 校验
两段，顺序固定：

1. `check-sources.ps1`（输入侧）：组件源存在性 + 版本闸门。非 0 退出码即 `throw`。
2. `verify-package.js`（产物侧）：用**产物内的便携 Node** 执行 `"$outDir\runtime\node\node.exe" "$PSScriptRoot\verify-package.js" --out $outDir --components $ComponentsFile`。非 0 退出码即 `throw`。用产物内 Node 的理由有两个：构建机无需预装 node；顺带验证便携 Node 可运行。`--layout` 不传，CLI 默认取 `tools\layout.json`。

### [5/5] 打包
除非 `-SkipZip`，先删旧 zip，再 `Compress-Archive -Path "$outDir\*" -CompressionLevel Optimal` 生成 `build\qdip-generic-<version>.zip`。

## 5. 校验体系

四层自动校验加一条手工自检。

### 输入侧：`tools/check-sources.ps1`

在复制**之前**检查构建输入，纯只读。

- 存在性：遍历 `components[]`，对每个 `source` 做 `Test-Path -LiteralPath`（`-LiteralPath` 兼容含空格/中文的路径）。有缺失逐条打印 `[FAIL]` 并 `exit 1`。
- 版本闸门：只对声明了 `verifyVersion` 的组件探测（源缺失时跳过探测，避免噪声）。探测失败或版本不符则打印 `[FAIL] version mismatch`、给出 `[HINT]`、`exit 1`。全绿打印 `[OK] all 11 component sources exist` 与 `[OK] version check passed: 2 component(s)`。

### 产物侧：`tools/verify-package.js`

零依赖（仅 `node:fs` / `node:path`）的产物校验器。它把「包布局」当契约来核对。

- 导出纯函数 `verifyPackage({ outDir, componentsFile, layoutFile })`：返回 `Array<{ rule, path, detail }>`，不打印、不抛异常、不写文件。违规记录形状固定，**没有 `severity` 字段**；`path` 一律是相对 `outDir` 的正斜杠路径（`env/unbound` 用启动器文件名）。
- 直接运行时是 CLI：`node tools/verify-package.js --out <outDir> [--components <file>] [--layout <file>]`。全绿打印 `[OK] package verified: <outDir>` 并 `exit 0`；有违规按 `rule` 分组打印 `[FAIL] <rule> (n)` 后 `exit 1`；参数缺失或读不到 `components.json` / `layout.json` 时打印到 stderr 并 `exit 2`。

九条规则：

| rule | 检查什么 |
|---|---|
| `layout/component-missing` | `components.json` 声明的每个 `target` 必须存在（文件或目录） |
| `layout/deploy-missing` | `layout.json` 的非 `optional` 条目必须按 `kind` 落位（`file` 是文件，`dir`/`emptydir` 是目录） |
| `layout/excluded-present` | 带 `exclude` 的条目 target 下，不应出现 basename 命中该模式的项（最小 glob，只支持 `*`） |
| `runtime/missing` | `runtime/node/node.exe` 存在；`opencode/bin/opencode.exe` 或 `opencode/bin/opencode.cmd` 至少一个存在 |
| `skills/missing` | 合并到同一 target 的多源组件：各源一级子目录名的并集必须都在 target 里 |
| `skills/collision` | 同一技能名同时出现在两个或以上源里 |
| `plugin/unresolved` | `opencode.json` / `tui.json` 的 `plugin` 数组中，以 `.` 开头的条目按该 JSON 所在目录解析后必须存在（npm 包名跳过） |
| `config/unparseable` | `opencode/config/opencode/` 下所有 `.json`（跳过 `node_modules`）必须能 `JSON.parse` |
| `env/unbound` | `opencode.json` / `tui.json` / `setup/config-writer.js` 中被引号包裹的 `{env:NAME}`，必须在 `env.bat` 里有 `set "NAME=` 绑定 |

技能库按**集合**而非数量判定，因为它由两个来源合并（见 `CONTEXT.md`）。

### 文档层：`tools/check-docs.js`

零依赖（仅 `node:fs` / `node:path`）的文档/地图层校验器，补上「文档层没有校验器」的缺口（本仓库发生过两次编码事故与两次文档死引用）。导出纯函数 `checkDocs({ repoRoot })`：返回 `Array<{ rule, path, detail }>`，形状与 `verify-package.js` 一致，不打印、不抛异常、不写文件；另导出 `describeScope({ repoRoot })` 暴露检查范围与跳过计数；直接运行时是 CLI（`node tools/check-docs.js [--repo <repoRoot>]`，先打印 `[SCOPE]`）。三条规则：

| rule | 检查什么 |
|---|---|
| `docs/path-missing` | include 文档（`codemap.md`、`tools/codemap.md`、`templates/codemap.md`、`templates/setup/codemap.md`、`README.md`、`AGENTS.md`、`CONTEXT.md`、`docs/adr/*`、`docs/整合包说明书.md`、`docs/发布前检查清单.md`、`templates/README.md`、`templates/玩家使用指南.md`）里反引号包裹的路径候选，必须能在某个基准上解析：**仓库根**（含去掉路径段内空格的二次尝试：带空格的 docs 路径先按原文解析、再按去空格形态解析一次）、**产物根**（首段属于 `opencode`/`plugins`/`runtime`/`mcp`/`setup`/`data` 的候选，相对最新 `build/qdip-generic-*` 解析，命中窄化运行时白名单也算过）、**basename 索引**（无 `/` 的裸文件名按仓库自有文件的 basename 核对）。以外部仓库/命令行为基准的片段走白名单 |
| `docs/encoding-broken` | 仓库自有文本文件（`.md`/`.js`/`.json`/`.txt`/`.bat`/`.ps1`/`.cjs`/`.mjs`）必须能按声明编码解码（`.bat` 按 GBK，其余按 UTF-8），且不含 U+FFFD 或私用区字符（U+E000–U+F8FF） |
| `docs/bom-missing` | `.ps1` 必须带 UTF-8 BOM；其余受检扩展名必须不带 BOM |

范围边界（已知盲区）：含 `*`/`?` 的 glob 片段、含 `...` 的省略写法（`tools/cache/...`）、含 `<...>` 的占位符（`opencode-<version>`）不做路径检查；`CHANGELOG.md` 只查编码不查路径（历史记录里的旧文件名允许已不存在）；历史规划文档（`docs/00-*`/`01-*`/`02-*`、`docs/matt-pocock-workflow-report.md`、`docs/workflow-diff-and-recommendations.md`、`docs/agents/*`）不在路径检查范围内；**没有构建产物时，产物路径整类跳过**（不报违规，但 `describeScope().skippedProductPaths` 会记数、CLI 会打印 `[WARN]`），因此文档层检查最好在 `build.ps1` 之后跑；`tools/cache/`、`build/`、`node_modules/`、`.git/`、`.superpowers/`、`release/` 不参与编码扫描与 basename 索引。

- `node --test "templates/setup/*.test.js"`：服务商契约、配置写入器与引导服务单测，当前 48 例。
- `tools/check-docs.test.js` 里有一条「真实仓库零违规」回归锁：`checkDocs({ repoRoot: <仓库根> })` 必须返回空数组。

产物校验在 `build.ps1` 的 [4/5] 阶段自动执行，不需要手动跑。注意必须用 glob 形式，原因见第 6 节。

### 手工自检：`启动.bat --check`

在产物目录里执行 `build\qdip-generic-<version>\启动.bat --check`，会真实调用 `env.bat` 并输出：

- `node.exe` 路径与版本
- `opencode` 的插件加载结果（`debug agent orchestrator`）
- Windows Terminal 发现结果（`:find_wt`）
- 工作目录（`WSDIR`）是默认包根还是玩家设定
- 缺失项的 `[FAIL]`（含 `env.bat missing`、`wt-profile.ps1 missing`）

这是改动启动器 / `env.bat` / 包布局后最值得跑的验证。

## 6. 已知约束与坑

**平台假设。** 全流程假定 Windows：PowerShell 脚本、`\` 路径、`node.exe` / `opencode.exe`、GBK 控制台。没有跨平台分支。

**`components.json` 含 5 个本机绝对路径。** `omoslim`、`omoslim-append`、`omo-skills`、`matt-skills`、`opencode-quota` 的 `source` 指向本机开发环境（`E:/云文件/...`、`C:/Users/Winde/...`）。移植构建机必须同步修改这 5 条。另外 6 条是仓库内相对路径（`tools/cache/...`）。

**编码约定，三类文件三种规矩：**

- `.bat` 一律 **GBK（代码页 936）+ CRLF**。cmd 在中文 Windows 下按 GBK 解析批处理，用 UTF-8 保存会毁掉中文（历史事故：`启动.bat --check` 误报 `进入环境.bat missing`）。编辑时用 PowerShell 按字节读写：`[System.Text.Encoding]::GetEncoding(936)`。**代码页陷阱**：cmd 按*当前控制台代码页*解释批处理文件里的字节，因此即便文件本身是 GBK，在 UTF-8 控制台（`chcp 65001`，或 Windows Terminal 配了 UTF-8）下，含中文的文件名字面量仍会被错误解码而误判（本次事故：`启动.bat --check` 误报 `进入环境.bat missing`）。**批处理里不要出现含中文的文件名字面量**；文件名完整性交给构建期断言（见第 4 节 [3/5]）。
- 仓库自有的 `.ps1` 一律 **UTF-8 with BOM**（`tools/build.ps1`、`tools/check-sources.ps1`、`templates/setup/wt-profile.ps1` 实测均为 BOM）。PowerShell 5.1 会把无 BOM 的脚本按 ANSI/GBK 解析，脚本里出现第一个中文字符就会变成语法错误。
- 其余文件（`.js` / `.json` / `.md` / `.txt`）UTF-8。

这三条约定现已由 `tools/check-docs.js` 的 `docs/encoding-broken` 与 `docs/bom-missing` 规则断言（`node --test "tools/check-docs.test.js"`），不再只靠人记。

**`node --test <目录>` 在 Node v24.14.1 下不可用。** 它会把目录当模块入口，报 `Cannot find module`（退出码 1）。必须用 glob 形式：`node --test "tools/*.test.js"`、`node --test "templates/setup/*.test.js"`。

**`opencode.json` 的配置键是单数 `provider`。** 1.18.27 起复数 `providers` 会被诊断为 unsupported 并静默丢弃。`config-writer.js` 也按单数写入。

**`instructions` 与 `plugin` 的相对路径基准不同。** `plugin` 按声明它的 JSON 文件所在目录解析；`instructions` 按 `process.cwd()` 解析并向上 `globUp`。启动器会把 CWD 切到玩家工作目录，所以 `instructions` 一律用 `{env:...}` 绝对路径 token，不用裸相对路径。详见 `docs/adr/0001-opencode-relative-path-resolution.md`。

**`layout.json` 不进产物。** 它是构建仓库内的声明；玩家机器上运行的 `config-writer.js` 读不到它，因此其 `rootOf()` 保留一份手写的布局副本，由构建仓库的测试锁定两边一致。详见 `docs/adr/0002-layout-json-stays-out-of-the-package.md`。

**MAX_PATH 风险。** 产物包含多层 `node_modules`（如 `plugins/oh-my-opencode-slim/node_modules/...`），加上包根自身路径，解压或构建时可能触及 Windows 传统 260 字符路径上限。把整合包放在靠近盘符根的浅目录（如 `D:\qdip`）可规避。

**部署条目的源缺失在构建期就被拦下。** `layout.json` 当前没有任何 `optional` 条目：非 `optional` 条目若 `source` 缺失，`build.ps1` 的 [3/5] 段会在复制前抛出 `部署条目 <name> 的源缺失`（见第 4 节），即使漏过，产物侧的 `layout/deploy-missing` 也会报。运行期的 `启动.bat --check` 只诊断玩家机器上的运行时依赖（node / opencode / 插件 / Windows Terminal / `env.bat` / `wt-profile.ps1`），不再检查产物文件是否存在——它不能出现含中文的文件名字面量（见上一条代码页陷阱）。

## 7. 常见维护任务

**升级 opencode。** 把新版离线包放到 `tools/cache/opencode-<version>`（用 `npm install --prefix` 后提取真实二进制），然后改 `tools/components.json` 里 `opencode-cli` 的 `source` 与 `version` 两处——`verifyVersion` 的 `args` 不用改。构建时闸门会拿 `opencode.exe --version` 与 `version` 比对。最后更新 `CHANGELOG.md`。产物内玩家侧的 `更新组件.bat` 走 `opencode-ai@latest`，与本清单无关。

**升级便携 Node。** 把官方发行版解压到 `tools/cache/node-v<version>-win-x64`，改 `node-runtime` 的 `source` 与 `version`（`version` 不带前缀 `v`；`verifyVersion.strip` 已声明 `v`）。

**增删技能。** 技能库有两个来源：`omo-skills`（本机 `C:/Users/Winde/.config/opencode/skills`）与 `matt-skills`（本机 `C:/Users/Winde/.agents/skills`），合并到产物 `opencode/config/opencode/skills`。新增技能放进对应源目录即可；构建后 `skills/missing` 会确认并集都落位，`skills/collision` 会在两个源出现同名技能时报错——**跨源重名必须改掉**，否则一个源的文件会覆盖另一个。`components.json` 里两个组件的 `version` 是人工标签，记得同步。

**新增一个受版本闸门保护的组件。** 在 `components.json` 的对应条目上加：

```json
"verifyVersion": { "exe": "<source 目录下的可执行文件名>", "args": ["--version"], "strip": "<可选，剥掉输出前缀>" }
```

前提是探针可执行、输出稳定、且输出（剥前缀后）恰好等于 `version`。闸门只在源存在时探测。

**新增一条部署条目。** 在 `tools/layout.json` 的 `deploy[]` 加一条 `{ name, kind, source, target }`（`optional` 可选）。`source` 相对仓库根，`target` 相对产物根。**不需要改 `build.ps1`**：它的 [3/5] 段就是遍历 `deploy[]` 按 `kind` 分派；同时 `verify-package.js` 的 `layout/deploy-missing` 会自动开始核对这条声明。若新增的是需要被 `env/unbound` 校验的环境变量，还要在 `templates/env.bat` 里加 `set` 绑定。

**移植到另一台构建机。** 至少做三件事：改 `components.json` 里 5 个本机绝对路径（见第 6 节）；把 `tools/cache/` 下的离线制品按 `source` 命名补齐（`node-v24.14.1-win-x64`、`opencode-1.18.30`、`omoslim-runtime/node_modules`、`quota-runtime/node_modules`、`chrome-devtools-mcp`、`terminal`）；确认构建机有可运行这些探针的 Windows 环境。构建机不需要预装 node（[4/5] 用产物内 Node）。

**发布一个新版本。** 逐条过 `docs/发布前检查清单.md`（维护者侧的发布前检查清单，含输入校验、组装、测试、产物校验、启动器自检、引导冒烟、端到端与归档）；改 `components.json` 的 `version`（它决定产物目录与 zip 名）；更新 `CHANGELOG.md`（在顶部加版本段，格式参照 Keep a Changelog）；从仓库根跑 `powershell -ExecutionPolicy Bypass -File tools\build.ps1`；把 `build/qdip-generic-<version>.zip` 归档到 `release/`。该目录已在 `.gitignore` 中——单个 zip 约 158 MB，超过 GitHub 的 100 MB 单文件上限，不能提交（也不要用 `git add -f` 绕过）。

## 8. 决策索引

术语表在 `CONTEXT.md`，逐条决策记录在 `docs/adr/`。已定下的关键设计选择：

| 决策 | 一句话理由 | 出处 |
|---|---|---|
| 包布局由 `layout.json` 单一声明 | 构建（[3/5]）与校验（`layout/deploy-missing`）读同一份声明，不会各写一份而漂移 | `tools/layout.json`、`tools/codemap.md` |
| `layout.json` 不进分发产物 | 玩家机器上运行的代码读不到它，且引入「缺失/损坏/被改」三条失败路径不划算 | `docs/adr/0002-layout-json-stays-out-of-the-package.md` |
| `config-writer.js` 的 `rootOf()` 保留为手写布局副本 | 它是**被校验的副本**：测试断言它写出的路径与 `layout.json` 声明一致，漂移即失败 | `docs/adr/0002-layout-json-stays-out-of-the-package.md` |
| 两段 seam：输入校验（`check-sources.ps1`）与产物校验（`verify-package.js`）分离 | 一个管输入、一个管输出，可各自独立运行与测试，都靠退出码接回 `build.ps1` | `tools/codemap.md`、`tools/build.ps1` [4/5] |
| 违规记录固定为 `{ rule, path, detail }`，无 `severity` | 形状稳定便于分组与断言；分级由 rule 本身表达 | `tools/verify-package.js` |
| 版本闸门只覆盖可机器读取的组件 | 闸门靠运行探针比对 stdout，只有 node / opencode 有稳定探针 | `tools/check-sources.ps1`、`tools/components.json` |
| 环境绑定集中在 `env.bat` | 启动器只 `call` 它；`env/unbound` 因此只对 `env.bat` 断言，避免两个启动器重复绑定与漏报 | `templates/env.bat`、`tools/verify-package.js` |
| 服务商契约单一来源（`contract.js`） | 浏览器与服务端共享同一份 `PROVIDERS` / 保留名 / 名称规则 / 模型表；`AVAILABLE_MODELS` 的键必须 ⊆ `PROVIDERS` 的键，键名错位不再可能 | `templates/setup/contract.js`、`templates/setup/contract.test.js` |
| `instructions` 用 `{env:...}` token 而非裸相对路径 | `instructions` 按 CWD 解析且启动器会切 CWD；token 由 `%~dp0` 每次推导，既脱 CWD 又耐搬运 | `docs/adr/0001-opencode-relative-path-resolution.md` |
| 技能库按集合比对（并集 + 跨源重名） | 它是两个来源合并的结果，数量不可靠 | `CONTEXT.md`、`tools/verify-package.js` |
| 文档层也有校验器（`check-docs.js`） | 路径死引用与编码事故各发生过两次；把「文档约定」从人记变成可测试断言 | `tools/check-docs.js`、`tools/check-docs.test.js` |

配套阅读：`codemap.md`（仓库总图）、`tools/codemap.md`（构建编排）、`templates/codemap.md`（分发模板）、`templates/setup/codemap.md`（服务商契约与引导服务三层）、`README.md`（维护者工作流）。
