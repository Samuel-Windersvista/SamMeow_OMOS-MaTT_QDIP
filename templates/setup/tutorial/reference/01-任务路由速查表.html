B两条判定心法

先钉清，再动手

只要存在一个需要人机对话的开放决策，先用 grill-with-docs 钉清——比事后返工便宜。拿不准大小，宁可先追问一轮。

拿不准就问路由器

不确定走哪条车道？先问 ask-matt，它会按情境推荐路径，并提醒哪些步骤必须在同一上下文窗口内完成。

C主链路速记

三条主链 -- 记住这三行就够用
单窗口  grill-with-docs → implement（tdd → code-review）
多窗口  grill-with-docs → to-spec → to-tickets → implement ×N
超大    wayfinder → 决策票循环 → to-spec

别塞错车道

大任务塞进小车道 = 中途上下文爆炸；小任务塞进大车道 = 十分钟的活干成半小时。拿不准就 grill 一轮。

D术语小词典

术语一句话
grill-with-docs有状态追问；边问边写 GLOSSARY.md 与 ADR
grilling追问原语：每轮抛出全部前沿问题
to-spec把对话综合成规格文档（不再追问）
to-tickets拆成垂直切片工单，声明阻塞关系
implement按工单实现；内驱 tdd 与 code-review
tdd红-绿-重构循环，只测约定的接缝
code-review双轴审查：仓库标准 + 原始规格
wayfinder超大工作的决策地图；每会话解决一票
diagnosing-bugs先建可复现循环，再修复
research后台代理查一手资料，产出引用笔记
customize-opencode修改 opencode 自身配置
ask-matt路由器：不确定走哪条车道就问它

E三个高频混淆对

场景车道
改项目里的文件（脚本、md、代码）单一小改动
改 ~/.config/opencode/ 下的系统文件配置 OpenCode
问题明确、只缺答案查资料
连问题本身都没定型超大规划
